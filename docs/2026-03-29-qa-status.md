## Open Issues

### LinkedIn captureSession Failure

**Severity:** High — blocks Lane 1/2 acceptance for auth-gated sites

**Symptom:** LinkedIn feed loads authenticated content when capture steps are run manually via `kuri.evaluate`/`kuri.navigate`, but returns `chrome-error://chromewebdata/` (HTTP 400) when the same steps run inside `captureSession()`.

**What works (manual):**
On a fresh managed headless Chrome launched by Kuri:
1. `kuri.newTab("about:blank")`
2. `kuri.navigate(tab, "https://www.linkedin.com")` (origin)
3. `kuri.setCookies(tab, vaultCookies)` (38 cookies from Comet)
4. `kuri.navigate(tab, "https://www.linkedin.com/feed/")`
5. Result: `Feed | LinkedIn` with real feed content — **every time**

Even with harStart, stealth script, interceptor script, and aggressive polling re-injection — manual still works.

**What fails (captureSession):**
The exact same Chrome instance, same tab creation method, same cookie injection — but orchestrated by `captureSession()` in `src/capture/index.ts`. Page shows `chrome-error://chromewebdata/` every time.

**Ruled out:**
- CSRF token as persistent header (removed, still fails)
- harStart destabilizing CDP (tested with harStart, manual still works)
- Stealth/interceptor scripts interfering (tested with all scripts, manual still works)
- Tab creation method (both use `kuri.newTab("about:blank")`)
- Cookie injection (logs confirm 34 cookies injected in both paths)

**Not yet investigated:**
- `forceProfileContext` option in captureSession (could change Chrome launch behavior)
- `waitForContentReady()` doing something that causes a navigation/redirect
- Tab cleanup/reset logic firing prematurely due to timeout
- `trySeedStructuredDocumentSkill`/`trySeedPublicDocumentFetchSkill` running HTTP fetches before captureSession that could affect Kuri state
- Whether `captureSession` is getting a DIFFERENT tab than expected (stale tab reuse)
- Exact timing differences between manual and automated paths

**Handoff bar:** Rach's acceptance says "LinkedIn/feed-style or equivalent auth-gated repros no longer fail because Kuri crashes or tabs never become usable." Kuri doesn't crash and tabs are usable (manual test proves it). The issue is capture orchestration, not Kuri/tab reliability.

```
FULL FLOW (what a user actually does):
══════════════════════════════════════

INSTALL:
  openclaw plugins install unbrowse-openclaw    ← Lane 3
  (or: npm install unbrowse)

SETUP:
  unbrowse health                               ← Lane 1 (Kuri starts, Chrome works)

AUTH:
  unbrowse login --url "https://linkedin.com"   ← Lane 2 (browser choice, cookie steal)
  (or: auto-detect from existing browser session)

FIRST RESOLVE (public site, no auth):
  unbrowse resolve --intent "search repos"      ← Lane 1 (capture pipeline)
    --url "https://github.com/search?q=openai"
  → Kuri launches Chrome
  → Navigates to page
  → Interceptor captures API traffic             ← Fix A (polling) + Fix B (perf replay)
  → Reverse-engineers endpoints
  → Publishes skill to marketplace
  → Returns structured data

FIRST RESOLVE (auth-gated site):
  unbrowse resolve --intent "get my feed"       ← Lane 1 + Lane 2
    --url "https://linkedin.com/feed/"
  → Kuri launches Chrome
  → Injects cookies from vault                   ← Lane 2 (cookie injection strategy)
  → Navigates to page (authenticated)
  → Captures API traffic or extracts from DOM
  → Returns structured data

SECOND RESOLVE (cached):
  unbrowse resolve --intent "search repos"      ← Lane 1 (marketplace reuse)
    --url "https://github.com/search?q=rust"
  → Hits marketplace cache
  → Executes learned endpoint directly
  → Returns in <200ms

PAID SKILL:
  unbrowse execute --skill <paid-id>            ← Lane 4
  → 402 challenge → pay → get data

OPENCLAW INTEGRATION:
  Agent says "find hiking trails near me"       ← Lane 3
  → OpenClaw routes to unbrowse plugin
  → Plugin spawns: unbrowse resolve --intent ...
  → Returns structured data to agent
```
