# Unbrowse x402 Payment API

Unbrowse routes can be monetized. When a route's creator opts in to
compensation, the paid endpoints answer with a standard **[x402](https://x402.org)**
`402 Payment Required` challenge: the caller pays, then retries with a payment
header, and the request executes.

This document covers the public contract — the endpoints, the challenge
envelope, and the two ways to pay. Indexing and reading routes are always free;
the 402 fires **only** when a route creator has explicitly opted in to
compensation (DNS-claimed + wallet-bound). There is no operator-level switch
that flips a free route into a paid one.

---

## 1. The flow

```
agent ──▶ GET /v1/skills/:id            (a paid surface)
        ◀── 402 Payment Required        { accepts: [ X402PaymentRequirementV2, … ] }
agent ──▶ pay (wallet signature OR bound api key)
agent ──▶ GET /v1/skills/:id            + X-PAYMENT header
        ◀── 200 OK                      (the skill / execution result)
```

### Paid surfaces

| Endpoint | Purpose |
|---|---|
| `GET  /v1/skills/:id` | Read a route manifest. Free unless the creator opted in; otherwise 402. |
| `POST /v1/skills/:id/execute` | Execute a route. Same gate. |
| `POST /v1/unlock` | Web-unblocker reseller — pay Unbrowse to front a cleared page fetch. Always 402-first. |

When no payment is presented and the route is paid, the server returns a `402`
with an `accepts[]` envelope describing how to pay. Re-send the same request
with a valid `X-PAYMENT` header (or an api key bound to a wallet — see §3) and
the request executes.

> The gate is purely price-driven: if a route's computed price is `0` (the
> default), every call returns `200` free. If the creator opted in and the price
> is non-zero, the call emits the 402 envelope. — *[shipped]*

---

## 2. The challenge envelope

The `402` body carries an `accepts[]` array. Each entry is an
`X402PaymentRequirementV2`:

```jsonc
{
  "scheme": "string",            // payment scheme identifier
  "network": "string",           // e.g. "solana" / "solana-devnet"
  "amount": "string",            // USDC base units (6 decimals), integer string
  "asset": "string",             // the payment asset (USDC mint)
  "payTo": "string",             // the route creator's wallet — the payee of record
  "maxTimeoutSeconds": 0          // how long the quote is valid
}
```

A full `402` response looks like:

```jsonc
{
  "x402Version": 2,
  "error": "payment_required",
  "resource": {
    "url": "https://api.unbrowse.ai/v1/skills/<id>",
    "description": "…",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "<scheme>",
      "network": "solana",
      "amount": "10000",
      "asset": "<usdc-mint>",
      "payTo": "<creator-wallet-address>",
      "maxTimeoutSeconds": 60
    }
  ],
  "facilitator": "faremeter-flex-solana"
}
```

- **`payTo`** is the **route creator's wallet** — the agent pays the creator
  directly. Unbrowse does not custody the funds.
- **Network (testnet vs mainnet)** is selected by `X402_NETWORK_MODE`
  (`mainnet` | `testnet`). When unset, it defaults to mainnet in production and
  testnet elsewhere. This only chooses which network the `accepts[].network`
  field references; it is **not** a payment on/off switch. — *[shipped]*

The challenge is also mirrored in a `PAYMENT-REQUIRED` response header
(base64-encoded JSON) for clients that read it there.

## 3. Two ways to pay (the headline)

A caller can satisfy the challenge in **either** of two ways. Both resolve to
the same notion — *who is the payer-of-record* — through one unified admission
boundary.

### (a) Wallet — sign the x402 authorization

Sign the x402 / Flex authorization (Solana USDC) and present it in the
`X-PAYMENT` header on the retry. The signer is the payer-of-record.

```bash
curl -X POST https://api.unbrowse.ai/v1/skills/<id>/execute \
  -H "Content-Type: application/json" \
  -H "X-PAYMENT: <base64-encoded-signed-x402-authorization>" \
  -d '{ "input": { … } }'
```

### (b) API key — the key wraps a wallet

Present a bearer api key:

```bash
curl -X POST https://api.unbrowse.ai/v1/skills/<id>/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <UNBROWSE_API_KEY>" \
  -d '{ "input": { … } }'
```

An api key is a **web2 wrapper around a wallet**. A key can be bound to a wallet
(via `setKeyFunding` with `{ kind: "wallet" }`), so the key *authenticates* the
request and the **bound wallet is the payer-of-record** — the caller does not
need a per-call wallet signature for the key to be recognized as a payer.

A key can alternatively wrap a **prepaid credit budget**
(`{ kind: "credit" }`), in which case the account pays by a server-side balance
decrement and there is no wallet of record.

### One admission boundary

Both modes flow through one recognition step — `admitPayment` — which returns:

```ts
{ admitted: boolean, payerWallet: string | null, lane: "wallet" | "api-key" | "credit" | "sponsor" | "none" }
```

Priority order (mirrors the live route): a signed `X-PAYMENT` proof (`wallet`)
→ a key bound to a wallet (`api-key`) → a key wrapping a credit budget
(`credit`) → platform sponsorship of a first call (`sponsor`) → none. This is
**pure detection**: it identifies the payer and the lane and moves no
funds. — *[shipped]*

## 4. Shipped vs. next

| Capability | Status |
|---|---|
| The `X402PaymentRequirementV2` challenge envelope + `accepts[]` on the paid surfaces (`/v1/skills/:id`, `/v1/skills/:id/execute`, `/v1/unlock`) | **[shipped]** |
| The unified admission boundary (`admitPayment` → `{ admitted, payerWallet, lane }`) recognizing wallet / api-key→wallet / api-key→credit / sponsor | **[shipped]** |
| Binding a wallet to a key (`setKeyFunding { kind: "wallet" }`) and to a credit budget (`{ kind: "credit" }`) | **[shipped]** |
| Wallet-signed settlement on the retry (`X-PAYMENT` → Flex facilitator) | **[shipped]** |
| API-key credit settlement (server-side balance decrement) | **[shipped]** |
| **API-key→wallet prepaid settlement** — the wallet deposits once (`POST /v1/account/keys/:id/deposit`, one signed x402), then the key pays per call from that prepaid balance, no per-call signature | **[shipped]** |
| **Non-custodial delegated settlement** — the key draws per call from the user's *own* on-chain escrow via a cap-bounded, expiring, revocable session key; funds never leave the user's custody | **[built — operator-activation-gated]** |

> **Honest scope note — two custody postures, both real:**
>
> - **Custodial-prepaid (shipped).** The bound wallet deposits USDC once; the key
>   then pays per call from that prepaid balance with no per-call signature. The
>   platform custodies the *deposited balance* (held in treasury, spent down per
>   call), never the wallet key. The unspent remainder is an IOU you trust the
>   platform to honor.
> - **Non-custodial delegated (built, activation-gated).** The wallet keeps its
>   funds in its *own* on-chain escrow and grants the platform a **cap-bounded,
>   expiring, on-chain-revocable** session key to draw within the cap. The platform
>   custodies *neither* the funds nor the wallet key; each draw's source is the
>   user's escrow, never treasury, and the splits are the verbatim challenge terms.
>   This lane is built and tested. It activates only once the operator configures
>   the delegation session key **and** the user has created+funded an escrow and
>   registered the session key on-chain; until then it is inert (a normal 402).

---

## Notes

- Amounts are USDC base units (6 decimals): `"10000"` = `0.01` USDC.
- The facilitator for Solana USDC settlement is **Faremeter Flex**
  (`faremeter-flex-solana`).
- New agents may have a first call covered by the platform (the `sponsor`
  lane); callers can opt out with `X-No-Sponsor: 1`.
