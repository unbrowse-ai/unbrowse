# Unbrowse v6.16 — Architecture & Delta-Reward Mechanics

**Released:** v6.16.0-preview.0 (2026-05-14)
**Tag:** [v6.16.0-preview.0](https://github.com/unbrowse-ai/unbrowse-dev/releases/tag/v6.16.0-preview.0)
**Status:** Preview — Phase 0+1 + partial Phase 5 shipped; preview.1+ completes deferred items
**Audience:** anyone integrating, deploying, or debugging the payment surface

This document is the canonical explanation of what shipped in v6.16, how the pieces fit, and how indexers earn proportional to the marginal value they add. For the API-shaped narrative read [`x402-flywheel.md`](./x402-flywheel.md); for the engineering plan read [`x402-routing-plan-v6.16.md`](./x402-routing-plan-v6.16.md).

## 1. What v6.16 changed in one paragraph

Unbrowse's settlement layer pivoted from **Corbits + Cascade Splits + direct-SPL sponsor transfers** to **Faremeter Flex** (`@faremeter/flex`). The new wire scheme carries multi-recipient splits *natively* in every signed authorization (up to 5 recipients × basis-points summing to 10000), so the platform's 10% cut + contributor payouts ride a single off-chain Ed25519 signature and settle on-chain in batches. Onboarding tightened: every agent must pair a wallet, fund a Flex escrow, and register a session key before getting an API key. Existing v6.15-era agents get a soft-block 402 (`X-Flex-Onboarding-Required: 1`) on priced routes until they complete the same flow. Cascade dependency removed from npm; Corbits codepath in `backend/src/middleware/x402-gate.ts` deleted (-414 LOC, 88% file shrink). Sponsor mode plumbed onto the Flex rail (opt-in via `SPONSOR_USE_FLEX_SPLIT=1`, off by default).

## 2. The wire layer — `@faremeter/flex`

### 2.1 Payment terms shape

When a priced route receives an unsigned request, the backend responds with a v2 x402 envelope (`backend/src/services/flex-payment-terms.ts:51`):

```json
{
  "x402Version": 2,
  "error": "Payment Required",
  "resource": { "url": "...", "description": "Skill access: <skill_id>", "mimeType": "application/json" },
  "accepts": [{
    "scheme": "@faremeter/flex",
    "network": "solana-mainnet",
    "amount": "<max_uc>",
    "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
    "payTo": "<agent_escrow_pda>",
    "maxTimeoutSeconds": 60,
    "extra": {
      "flexAuthorizationDraft": { "escrow", "mint", "maxAmount", "authorizationId", "expiresAtSlot", "splits" },
      "splits": [{ "recipient": "<platform_ata>", "bps": 1000 }, ...],
      "programId": "<FLEX_PROGRAM_ADDRESS>"
    }
  }]
}
```

### 2.2 Signing path

The SDK catches `PaymentRequiredError`, calls `payAndRetryFlex(error, wallet, retry)` (`packages/sdk/src/flex.ts:200`). The wallet's session key signs the authorization with `signPaymentAuthorization` from `@faremeter/flex-solana`; the resulting `FlexPaymentPayload` is base64-encoded into an `X-PAYMENT` header. The backend verifies via the platform's Flex facilitator (`backend/src/services/flex-facilitator.ts:133` `createFlexFacilitator` wrapping `createFacilitatorHandler` from `@faremeter/payment-solana/flex/facilitator`).

### 2.3 Settle path

Facilitator runs `handleVerify(requirements, payload)` → hold reserved in memory → route executes the skill → facilitator's `handleSettle` finalizes the actual amount used (≤ `maxAmount`). Background `flush()` (opportunistic `c.executionCtx.waitUntil()` in preview.0; scheduled cron in preview.1+) submits batched on-chain transactions. After the refund window, `finalize` distributes the USDC per the signed `splits` array.

## 3. Indexer rewards — delta-based proportional share **(YES, implemented)**

This is the answer to "is delta-difference-based rewards per indexer implemented?" — yes, end-to-end. Here's the chain.

### 3.1 What "delta" means

When an agent executes a skill, two scores are computed:

- **`reliability_score ∈ [0, 1]`** — success rate of THIS endpoint (this indexer's route)
- **`next_best_score ∈ [0, 1]`** — success rate of the next-best alternative endpoint from a DIFFERENT indexer for the same skill

Then:

```
delta_score = clamp(reliability_score - next_best_score, 0, 1)
```

(`backend/src/services/attribution.ts:89` `computeAttribution`)

**Intuition**: an indexer's marginal contribution is *how much better their route is than the next-best alternative*. If reliability = 0.9 and next-best = 0.85, delta = 0.05 (small unique value). If reliability = 0.9 and next-best = 0.2, delta = 0.7 (this indexer is uniquely valuable — no good alternative exists). If reliability ≤ next_best, delta = 0 (this route adds nothing unique).

### 3.2 Per-execution credit + decay

On every successful execute, the backend's stats route (`backend/src/routes/stats.ts:281-294`) fires (waitUntil, non-blocking):

```ts
recordAttribution(env, {
  execution_id, skill_id, endpoint_id, indexer_id,
  reliability_score: successful / total,
  next_best_score: body.next_best_score ?? 0,
}).then(event => updateContributorDelta(env, skill_id, indexerId!, event.delta_score));
```

`recordAttribution` (`attribution.ts:104`) writes per-indexer ledger rows at `attribution:indexer:<indexer_id>` in KV:

```ts
ledger.total_credited_uc   += fee_allocated_uc;       // BASE_FEE_UC + DELTA_BONUS_UC * delta_score
ledger.execution_count++;
ledger.cumulative_delta    += delta_score;             // raw sum (audit trail)
ledger.avg_delta            = cumulative_delta / execution_count;
ledger.last_attributed_at   = now;
```

`updateContributorDelta` (`splits.ts:245`) then updates the SKILL's per-contributor `cumulative_delta` with **exponential decay**:

```ts
const DELTA_DECAY_RATE   = 0.95;  // 5% decay per execution
const MIN_DELTA_THRESHOLD = 0.01; // contributors below this are pruned

for (const c of contributors) c.cumulative_delta *= DELTA_DECAY_RATE;  // all decay
contributors[idx].cumulative_delta += deltaScore;                       // active credit
contributors = contributors.filter(c => c.cumulative_delta >= MIN_DELTA_THRESHOLD);
```

**Effect**:
- Active contributors (routes frequently chosen with high marginal value) grow their share
- Inactive contributors (routes replaced by better ones) decay to near-zero in ~60 executions
- Contributors below threshold are pruned entirely

### 3.3 Splits computation reads `cumulative_delta`

When a paid execute fires, `computeFlexSplits` (`backend/src/services/flex.ts:49`) sorts contributors by `cumulative_delta` (highest first), takes the top 4 (5 max minus 1 for platform), and weights bps proportionally:

```ts
const sorted = [...payable].sort((a, b) => b.cumulative_delta - a.cumulative_delta);
const eligible = sorted.slice(0, FLEX_MAX_SPLITS - 1);  // top 4 contributors

const totalDelta = eligible.reduce((s, c) => s + Math.max(c.cumulative_delta, 0.01), 0);
const contributorPool = 10000 - PLATFORM_BPS;  // 9000 bps for contributors

const contributorSplits = eligible.map(c => ({
  recipient: c.wallet_address,
  bps: Math.round((c.cumulative_delta / totalDelta) * contributorPool),
}));

return [{ recipient: platformRecipient, bps: PLATFORM_BPS }, ...contributorSplits];
```

The largest contributor gets the largest share of the 9000 bps pool. Normalization on the last line ensures bps sum to exactly 10000.

### 3.4 Concrete example

Skill `weather-api` has three contributing indexers:

| Indexer | recent delta history | `cumulative_delta` (post-decay) | bps share | $1.00 paid call earns |
|---|---|---|---|---|
| Platform | — | — | 1000 (fixed) | $0.100 |
| Alice (founded the skill) | 0.6, 0.5, 0.4, 0.3 trending down | 1.20 | ~3375 | $0.338 |
| Bob (latest improvement) | 0.0, 0.0, 0.7, 0.8 trending up | 2.10 | ~5906 | $0.591 |
| Carol (no recent wins) | 0.3, 0.0, 0.0, 0.0 | ~0.02 (below threshold) | 0 | $0.000 |

Bob earns the most because his recent routes were unique (high marginal value vs. Alice's). Alice still earns because her cumulative history hasn't decayed away. Carol is pruned — her routes have been superseded.

### 3.5 What enforces honesty?

- **`next_best_score` is computed by the marketplace**, not self-reported. The orchestrator queries the second-best alternative at execute time.
- **Decay is unconditional** — every execution decays ALL contributors, even the one being credited. Sybil-creating contributor accounts can't escape decay.
- **`MIN_DELTA_THRESHOLD`** drops dead weight before it dilutes shares.
- **`FLEX_MAX_SPLITS = 5`** caps recipients per authorization (Flex protocol constraint) — at most platform + 4 contributors per skill.

### 3.6 The fee_allocated_uc — additional per-execute earnings

Beyond the on-chain split distribution at settle time, indexers earn a **per-execution attribution fee** (`attribution.ts:94`):

```ts
fee_allocated_uc = BASE_FEE_UC + Math.round(DELTA_BONUS_UC * delta_score);
```

This is credited to the indexer's `total_credited_uc` ledger row immediately (synchronous, in `STATS_KV` at `attribution:indexer:<id>`). When credits are enabled (`CREDITS_ENABLED=1`), the amount is also rolled into the indexer's credit balance via `creditEarnings`.

This is a SEPARATE income stream from the on-chain Flex settlement:
- **Flex settlement** = USDC paid by the agent (or sponsor) → on-chain distribution per `cumulative_delta`-weighted splits → indexer's wallet ATA
- **Attribution fee** = µ¢ credited to the indexer's account ledger (no on-chain tx) → withdrawable later

Both update on the same execution.

## 4. Onboarding gate — wallet + escrow + session key

### 4.1 Why three steps?

Flex requires the agent to:
1. **Pair a wallet** — a Solana address that owns the escrow PDA and signs on-chain ops
2. **Fund a Flex escrow** — pre-deposit USDC into a PDA owned by the agent + facilitator
3. **Register a session key** — an Ed25519 keypair stored locally that signs payment authorizations *off-chain* (so the agent never signs with the wallet's main key on every request)

Without all three, the agent can't sign valid authorizations, so the platform can't process a paid call.

### 4.2 Where the gate enforces

| Surface | Behavior |
|---|---|
| `unbrowse setup` CLI | Honest-skip wizard (`src/runtime/setup.ts`): prints SDK + web URLs for each missing step; ends with "Onboarding partial — priced calls will receive 402" |
| `POST /v1/agents/register` | Returns 400 `{error: "flex_onboarding_incomplete", missing: [...]}` if any of the three fields is empty (`backend/src/routes/agents.ts`) |
| Priced routes (`/skills/:id/execute`, `/v1/execute`, `/search`) | Returns 402 `X-Flex-Onboarding-Required: 1` for legacy v6.15 agents missing fields (`backend/src/middleware/flex-onboarding-soft-block.ts`) |
| Free routes (`/health`, `/search` read-only) | Skip the gate; legacy agents can still inspect their account |
| `/account` UI | Three sequential CTAs: Pair wallet → Fund escrow → Register session key (`frontend/src/app/account/{wallet,escrow,session-key}/page.tsx`) |

### 4.3 `AgentProfile` schema additions

`backend/src/types.ts`:
```ts
interface AgentProfile {
  // ... existing fields ...
  wallet_address?: string;
  flex_escrow_address?: string;       // base58 PDA
  flex_session_key_address?: string;  // base58 Ed25519 pubkey
  flex_facilitator?: string;          // override default facilitator
}
```

All three new fields are optional in the type (backward-compat with legacy rows) but required at registration.

## 5. Sponsor mode on Flex rails

### 5.1 What it does

When `SPONSOR_USE_FLEX_SPLIT=1`, the platform-owned sponsor escrow signs Flex authorizations on the agent's behalf using a sponsor session key. Caps and decision logic in `sponsor.ts` `maybeSponsor` are unchanged from v6.15:

1. `X-No-Sponsor` header → `opted_out`
2. `sponsorWalletReady(env)` → `exhausted/no_wallet`
3. Per-agent daily cap (default $1) → `exhausted/agent_cap`
4. Per-platform daily cap (default $50) → `exhausted/global_cap`
5. Otherwise → call `sendSponsorFlexPayment` to sign

**Crucial**: caps fire BEFORE signing (Day-8 audit Slice 8 confirmed). Test `backend/tests/sponsor-flex-caps.test.ts` pins this order.

### 5.2 Why off-by-default in preview.0?

v6.15 shipped a "$1/day on the house" narrative. Flipping the rail mid-cycle would change the on-chain footprint (sponsor pays from escrow vs. direct SPL transfer) and risks blanking the v6.15 metric continuity. Off-by-default preserves cold-start behavior; flip when sponsor escrow funding + telemetry confirm parity.

### 5.3 Recoup

The sponsor authorization carries the AGENT's skill splits (including the platform's 1000 bps). So when the platform signs a $1.00 sponsored call:
- Platform pays $1.00 principal from sponsor escrow
- On-chain distribution: $0.90 to creator, $0.10 back to the platform recipient ATA
- Net platform cost: $0.90 per sponsored call (vs. $1.00 under v6.15's direct-SPL transfer)

10% recoup. Documented in [`x402-flywheel.md`](./x402-flywheel.md) section 4.

Returns sponsor settlement rows from `sponsor:ledger:*` KV keys. ADMIN_KEY-gated. Each row carries `agent_id`, `skill_id`, `amount_uc`, `creator_wallet`, `settled_tx`, `payment_method: "flex" | "direct_spl"`, `authorization_id` (when Flex).

### 8.4 Indexer attribution surfaces (existing, pre-v6.16)

## 9. Migration notes for builders

### 9.1 If you call us via SDK

```ts
import { Unbrowse, PaymentRequiredError } from "@unbrowse/sdk";
import { payAndRetryFlex } from "@unbrowse/sdk/flex";

const u = await Unbrowse.local();
try {
  const r = await u.execute(skill, input);
} catch (e) {
  if (e instanceof PaymentRequiredError) {
    // Use the new Flex retry helper
    const r = await payAndRetryFlex(e, wallet, (header) =>
      u.execute(skill, input, { headers: { "X-PAYMENT": header } }));
  }
}
```

`Unbrowse#executeMetered` exists but throws a version-targeted error until preview.2 ships the route.

### 9.2 If you call us via HTTP

The 402 envelope now has `scheme: "@faremeter/flex"` and `extra.flexAuthorizationDraft + splits + programId`. Sign an Ed25519 authorization with your session key against the platform's `FLEX_PROGRAM_ADDRESS`, base64-encode a `FlexPaymentPayload`, pack into `X-PAYMENT`. See [`x402-flex-migration.md`](./x402-flex-migration.md).

### 9.3 If you onboard new agents

`POST /v1/agents/register` requires `{email, wallet_address, flex_escrow_address, flex_session_key_address}`. Missing any → 400 with `missing[]`. Walk users through `unbrowse setup` (CLI) or `/account/{wallet,escrow,session-key}` (web).

## 12. Footnotes & known imprecisions

- **`computeFlexSplits` uses `wallet_address` as the recipient, but Flex spec wants the USDC ATA.** TODO comment in `flex.ts:66`. Works today because the ATA lookup happens facilitator-side; will be tightened in preview.1.
- **`createFacilitatorHandler` adapter loss**: Faremeter's `flush()` returns `FlushResult[]` (per-authorization); our wrapper counts `submitted` but doesn't surface `finalized` count (Faremeter runs finalization on its own `setInterval`). For Cloudflare Worker isolates, that setInterval doesn't survive between requests, so finalization runs only when route handlers call `flush()`. Preview.1's scheduled cron fixes this.
- **`computeContributorShares` in `splits.ts:23` uses a 100-share model** (legacy Cascade). `flex.ts:computeFlexSplits` uses the bps model (10000-share). Both still exist; the routes call the bps version. Phase 5 deletion of `splits.ts` retires the 100-share function with the rest.
