(commit 2817cb8c) was deployed (staging build_sha=2817cb8c). Retrieval coverage is again **0/21**,
but the ROOT CAUSE has MOVED and that is the headline:

- **Prior run:** 0/21 because of the split-brain BUG — the bm25 index wrote/read the EMPTY
  Cloudflare KV while everything else used EmergentDB. A real defect.
- **This run:** the split-brain is FIXED (verified: index read+write now both go to
  skillsKV->EmergentDB; the adapter round-trips). 0/21 is now because the EmergentDB index is
  **EMPTY** — `staging-skills-v3:bm25-idx:*` returns found=False for global + per-domain keys.
  Nothing has populated it.

**Why the bench can't move the number:** the corpus harness drives `resolve` + `resolve_execute`
(read + replay). It does NOT `capture->publish` (act go->snap->close), which is the ONLY path that
writes `bm25-idx` (reindexSkill on publish). So the bench measures resolve coverage against
whatever is already indexed — and nothing is. Populating requires REAL capture sessions on sites
that yield publishable endpoints; this corpus is content sites (no internal API) + anti-bot-gated
API sites, which don't publish. (Same corpus limitation recorded prior.)

**Net:** the indexing defect is closed and shipped; coverage is index-data-bound, not code-bound.
The true populate proof is an in-worker capture->publish then resolve>0 — pending a publishable
capture, not a code gap.
